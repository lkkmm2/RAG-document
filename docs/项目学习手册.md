> 这份文档的目标：让你在面试前把项目"吃透"，能指着任意一个文件说清楚

> 配套阅读：[面试问答.md](面试问答.md)（直接背的问答）· [演示指南.md](演示指南.md)（5 分钟演示脚本）。

## 一、项目是什么

一个**可评测、可观测**的文档问答系统。用户上传 PDF/TXT/Markdown，系统解析、切分、向量化入库，
提问时先检索再让大模型基于检索结果作答，并给出可点击的引用来源。

一句话定位（简历/自我介绍用）：

> 基于 RAG 的中文文档问答系统，自建评测集驱动优化：混合检索（向量 + BM25）+ RRF 融合 +
> Cross-Encoder 精排 + 父子块上下文，recall@4 从 0.70 提升到 0.90、MRR 0.54→0.76；
> 带引用校验与 ReAct Agent，FastAPI + Streamlit 前后端分离，Docker 部署。

**它不是什么**：不是"调个 API 的 Demo"，也不是"训练大模型"。核心价值在**检索质量**和**工程闭环**。

## 二、5 分钟跑起来

```powershell
# 1) 依赖（Python 3.10+，建议 3.12）
python -m venv .venv
.\.venv\Scripts\activate
pip install -e ".[dev,cn]" -i https://pypi.tuna.tsinghua.edu.cn/simple

# 2) 配置 Key（没有 Key 会自动降级成 Mock 模式，链路仍可跑通）
copy .env.example .env
#   编辑 .env，填 DOCQA_LLM__API_KEY=sk-xxxx

# 3) 入库（首次会下载 bge 模型约 95MB）
python -m docqa.cli

# 4) 起服务
python -m uvicorn docqa.api.main:app --port 8000      # 后端 + Swagger: http://127.0.0.1:8000/docs
python -m streamlit run apps/web/app.py               # 前端: http://127.0.0.1:8501
```

没有 Docker 也能跑；有 Docker 时 `docker compose up --build` 一次起两个服务。

**首次启动会做什么**：建 `data/index/` → 加载 embedding 模型（95MB，缓存到 `data/models/`）→
从 `chunks.jsonl` 重建 BM25 → 装配各层。精排模型（1GB）是**懒加载**的，第一次检索才拉。

## 四、一次问答的完整链路

以"休学最长可以多久？"为例，从点击发送到看到回答：

```text
前端 Streamlit
  └─ POST /api/v1/ask/stream  {question, history, top_k}
       │
       ├─[1] 中间件：分配 trace_id，记录开始时间，限流检查
       │
       ├─[2] QueryRewriter.rewrite()
       │     无历史 → 原样返回（省一次 LLM 调用）
       │     有历史且有指代 → LLM 改写成独立问题
       │
       ├─[3] embed_query()
       │     bge 模型，query 侧加"为这个句子生成表示以用于检索相关文章："
       │
       ├─[4] Chroma 向量召回 top-20   ← 语义相近
       │     BM25 召回 top-20         ← 字面精确（"休学""复学"）
       │
       ├─[5] RRF 融合：score = Σ 1/(60+rank)
       │     输出候选 top-20（两路都命中的排前面）
       │
       ├─[6] Cross-Encoder 精排：20 条 (query, chunk) 逐对打分 → top-4
       │     模型不可用 → 自动降级为融合顺序，不报错
       │
       ├─[7] 父块回溯 + 去重
       │     子块命中 → 取它所属的 1200 字父块（同一父块只留一条）
       │     按 max_context_chars=4000 截断
       │
       ├─[8] 组装 Prompt
       │     [1] 《手册》第X章 · 第N页 \n 正文...
       │     系统提示：只依据资料、句末标 [n]、没有就说"文档中未提及"
       │
       ├─[9] LLM 流式生成 → SSE 逐字推送
       │
       └─[10] 引用校验：解析 [n]，检查 n 是否在 1..4 内
              非法编号 = 幻觉信号，记 warning 并写进响应
```

整条链路在本地 CPU 上：检索 30-80ms，生成取决于模型（DeepSeek 首 token 约 0.5-1.5s）。

## 五、逐层设计说明

### 5.1 配置层（config.py）

**三层优先级**：显式传参 > `DOCQA_*` 环境变量 > `.env` > `configs/config.yaml` > 代码默认值。

为什么这么设计：
- 分块大小、Top-K 是**实验参数**，放 YAML，做对比实验改一行；
- Key、端口是**环境相关**，走环境变量，不进仓库；
- 三层都有默认值 → 删掉 YAML、没有 `.env` 也能起来（自动降级 Mock）。

实现关键：`YamlSettingsSource` 把 YAML 接进 pydantic-settings 的取值链，
而不是"先读 YAML 再手动覆盖"——后者会丢掉 pydantic 的校验和类型转换。

> 面试可讲：`DOCQA_RETRIEVAL__FINAL_TOP_K=6` 这种双下划线嵌套环境变量，
> 是 pydantic-settings 的 `env_nested_delimiter`，容器里改参数不用动镜像。

### 5.2 解析与清洗（ingest/loader.py + cleaner.py）

- **文本引擎 pypdf**：线性扫描，272 页 4.3 秒。pdfplumber 按坐标布局解析，一页 1-2 秒，
  272 页要几分钟，所以只把表格抽取做成开关（默认关）。
- **不做 OCR**：扫描件只做检测（平均每页 < 30 字 → 告警），把"上 PaddleOCR/多模态"留给迭代。
  这比硬塞一个识别率不稳的 OCR 更诚实，面试也更好讲"我知道边界在哪"。
- **清洗三件事**：
  1. 页眉页脚：统计每页前两行/后两行的跨页重复率，超过 60% 页面出现的行删掉。
     （实测删掉了 1 种："学生手册"——它原本会出现在每个 chunk 里，把向量稀释掉。）
  2. 纯页码行、纯符号行；
  3. 断行修复：PDF 抽出来的硬换行，如果上一行不是标题、不以句末标点结尾，就接回去。

> 为什么这一步重要：页眉"学生手册"四个字进了 800 个 chunk，任何问题都能匹配到每一页，
> 召回看起来很高但全是噪声。这类"隐形降噪"是 RAG 效果的分水岭。

### 5.3 切分（ingest/splitter.py）★

三层结构：

```text
全文
 └─ 章节块（按标题切，保留 section 路径：第二章 学籍管理 > 第二节 学籍异动）
     └─ 子块 400 字（递归分隔符 + 80 字重叠）→ 被检索，带 section/page 元数据
         └─ 父块 1200 字（跨章节聚合 7-8 个子块）→ 被喂给模型
```

关键实现点：

| 问题 | 做法 |
|---|---|
| 怎么切不切断句子 | 递归分隔符优先级 `\n\n → \n → 。→ ！→ ？→ ；→ ，→ 硬切` |
| 怎么保证块大小 | 先切成"原子片段"，再贪心装箱到 `chunk_size`，装不下就开新窗口 |
| 怎么重叠 | 新窗口从上一窗口末尾回退 `overlap` 字，且回退到句子边界 |
| 碎片怎么办 | 小于 `min_chars` 的块**并进前一块**（不丢弃，避免丢内容） |
| 只有标题的块 | 丢弃——它的文字已在子块的 section 路径里，留着就是 8 字孤儿块 |
| 页码怎么来 | 全文拼接时记录每页起始偏移，切分后用 `bisect` 把字符偏移映射回页码 |
| 父块为什么跨章节 | 制度文档一章才一两百字，父块按章切就和子块一样大，small-to-big 直接失效 |

实测（272 页学生手册）：851 个章节块 → 874 个子块（均 178 字）→ 118 个父块（均 1309 字，
每父块 7.4 个子块）。

> 这是全项目最值得讲的一段：**"小块检索、大块生成"不是一句口号，
> 父块如果没比子块大，就等于没做。**

### 5.4 向量化（embedding/embedder.py）

- 模型 `BAAI/bge-small-zh-v1.5`：512 维，95MB，CPU 上 874 块约 30 秒。
  选它不选 bge-m3（2.2GB）：**延迟和内存**换一点点召回，本科项目场景更划算，且配置可切。
- **query 加指令前缀、passage 不加**：bge 是非对称检索训练出来的，推理时保持一致，
  相似度分布才对得上。
- 归一化后算余弦 → Chroma 用 `hnsw:space=cosine`，`score = 1 - distance`。
- `HashingEmbedder`：字符 n-gram 哈希，零依赖、确定性，专供单元测试和离线兜底。
  **测试不下载模型**是这套设计最实际的收益（45 个测试 10 秒跑完）。

### 5.5 存储（store/）

三个文件，职责分明：

| 文件 | 角色 | 能否重建 |
|---|---|---|
| `chunks.jsonl` | 事实源：所有子块 + metadata | 否（丢了要重新解析） |
| `chroma/` | 派生索引：向量近邻 | 能（从 chunks 重算） |
| `manifest.json` | 快照：哪个模型、什么分块参数 | — |

**为什么不全塞进 Chroma**：向量库是索引不是数据库。换 embedding 要重建索引，
但原文不该跟着丢；BM25 需要全量文本；评测要对齐 gold chunk id 需要能直接 diff 文件。

**manifest 的价值**（真实坑）：模型换了但索引没重建，检索结果会"看起来正常但明显变差"，
极难排查。启动时比对 manifest 里的 `embedding_model/chunk_size`，不一致直接 warning。

### 5.6 检索（retrieval/pipeline.py）★

四步，每步都能单独关掉做消融：

1. **双路召回**：向量 top-20（语义）+ BM25 top-20（字面）。
   BM25 用 jieba 分词 + `BM25Okapi(k1=1.5, b=0.75)`，自带停用词表（但保留"学籍"这类领域词）。
2. **RRF 融合**：`score(d) = Σ weight_i / (k + rank_i(d))`，k=60。
   选 RRF 不选分数加权：余弦相似度是有界值、BM25 是无界实数，量纲对不齐，
   加权就得调归一化 + 权重，换模型要重调；RRF 只看名次，跨模型更稳。
3. **Cross-Encoder 精排**：`bge-reranker-base`，对 20 条逐对打分取 top-4。
   bi-encoder 是"各自编码再算余弦"，没见过彼此；cross-encoder 逐词交互，判断更准但只能实时算。
   **懒加载 + 失败降级**：模型加载失败/推理异常 → 退回融合顺序，请求不失败。
4. **父块回溯 + 去重**：子块命中后取父块正文（上下文完整），同一父块只保留分数最高的一条
   （否则同一段 1200 字会被喂两遍，浪费 token 还稀释注意力）。

**上下文预算**：`max_context_chars=4000`，超了从低分的开始截。

### 5.7 生成与引用（rag/）

系统提示的三条硬约束：只依据资料、句末标 `[n]`、没有就答"文档中未提及"。

**引用校验**（`validate_citations`）：
- 解析回答里所有 `[n]`，检查是否落在 `1..len(contexts)`；
- 非法编号 = 模型引用了不存在的来源 = 幻觉信号，记 warning；
- 顺便算 **coverage**：带引用的句子占比，评测里当可信度指标。

**检索为空时直接返回"未提及"，不调模型**：省钱 + 避免模型开始编。

**流式**：`answerer.stream()` 是个生成器，依次 yield `retrieval / delta / done / error` 四类事件，
API 层转成 SSE（`data: {...}\n\n`），前端 `iter_lines` 逐条消费。

### 5.8 Agent（agent/react.py）★

手写 ReAct 循环：`system prompt（工具清单 + JSON 输出协议） → 模型输出 {thought, action, action_input} → 解析 → 执行工具 → 观察结果回灌 → 下一轮`。

四个工程细节：

1. **终止条件不止步数**：`max_steps` + 无进展检测（同工具同参数重复 > 2 次直接熔断）
   + `max_tool_calls` + 模型主动 `final_answer`。
2. **工具失败要回灌**：参数错 → "参数不正确，请检查参数名"；执行异常 → "工具失败，换个方式"。
   不能抛异常结束任务——模型有能力自我纠正，前提是你把错误告诉它。
3. **JSON 容错解析**：直接 `json.loads` → 去 ```json 代码块 → 扫第一个平衡括号。
   模型偶尔会加"好的，我来检索："这种前缀，不能让格式问题毁掉整个任务。
4. **引用全局重编号**：每次 `search_docs` 内部编号从 1 开始，第 2 次调用会和第 1 次撞车。
   所以返回时把 `[1]` 映射成全局编号 `[5]`，用户在 UI 上点引用才对得上。

四个工具：`search_docs`（检索）、`list_documents`、`read_section`（按章节标题直读）、
`calculator`（`ast` 白名单求值，**绝不用 eval**——模型输出是不可信输入）。

### 5.9 接口层（api/）

10 个端点，重点四个：

| 端点 | 为什么存在 |
|---|---|
| `POST /ask` | 标准问答，返回完整 JSON（含 debug 字段） |
| `POST /ask/stream` | SSE 流式，"首 token 时间"是产品需求 |
| `POST /search` | **纯检索，不花 token**——调试召回和跑评测都用它 |
| `POST /agent` | 多步任务 |

中间件做三件事：trace_id（响应头回写 `X-Trace-Id`，出问题能按 id 串日志）、
耗时统计（`X-Process-Time`）、进程内令牌桶限流。

异常统一成 `{code, message, trace_id, detail}`；`DocQAError` 自带 `http_status`，
路由里不用写 try/except 拼错误信息。

自建 `/docs`：官方 Swagger UI 走 Google CDN，国内经常白屏，换成 bootcdn。
（这是 v1 就有的做法，保留并在文档里说明了原因。）

### 5.10 评测（eval/）★

四个指标，各有明确用途：

| 指标 | 定义 | 用来回答什么问题 |
|---|---|---|
| `recall@k` | gold chunk 是否在前 k 条 | 检索有没有捞上来 |
| `MRR` | 第一个正确结果排名倒数 | 正确结果排得靠不靠前 |
| `keyword_hit` | 答案命中 gold 关键词比例 | 回答对不对（廉价代理） |
| `citation_precision` | 引用里 gold chunk 占比 | 引用是不是真依据 |
| `refusal_accuracy` | 无答案题正确说"未提及"比例 | 会不会硬编 |

**评测集怎么来的**（这是最容易被追问的点）：
人工写"问题 + 标准答案 + 3 个高区分度关键词"（如"累计不得超过两年"），
`scripts/build_eval_set.py` 按关键词在 874 个 chunk 里定位，自动回填 `gold_chunk_ids`。
好处：gold 标注可追溯、可复查；关键词太通用（命中 > 5 个 chunk）会被判"区分度不足"并告警。

**消融实验**：`scripts/eval.py --presets vector_only,hybrid,hybrid_rerank`
只翻开关、不重建索引，跑出对比表——这就是"混合检索提升了多少"的证据。

## 六、配置项速查

| 参数 | 默认 | 调大会怎样 | 调小会怎样 |
|---|---|---|---|
| `chunking.chunk_size` | 400 | 上下文更完整，检索精度下降 | 精度高但易断章取义 |
| `chunking.chunk_overlap` | 80 | 边界信息更全，索引变大 | 答案被切断概率上升 |
| `chunking.parent_size` | 1200 | 生成上下文更全，token 更贵 | 退化成普通切分 |
| `retrieval.vector_top_k` | 20 | 召回率高，精排变慢 | 快但可能漏 |
| `retrieval.final_top_k` | 4 | 信息多但噪声多、贵 | 省 token 但可能缺依据 |
| `retrieval.rrf_k` | 60 | 融合更平缓（名次影响小） | 更偏向头部结果 |
| `retrieval.mmr_lambda` | 1.0 | — | 越小越去冗余（多样性↑） |
| `rerank.enabled` | true | 精度↑、延迟↑ | 快但精度降 |
| `api.rate_limit_per_min` | 120 | 更宽松 | 更严格，0 = 关闭 |

## 七、常见问题排查

| 现象 | 先看哪里 |
|---|---|
| 答"文档中未提及"，但文档里明明有 | `POST /search` 看召回；没有 → 切分/embedding 问题；有 → Prompt 或 final_top_k |
| 召回全是同一页 | 页眉页脚没删干净 → 看 `clean_pages` 日志里的"已移除疑似页眉页脚" |
| 上传后检索不到 | `manifest.json` 的 embedding 模型是否和当前配置一致 |
| 换了模型效果变差 | 同上，索引没重建 |
| 首 token 很慢 | 看 `timings_ms`：retrieval 慢 → 精排；生成慢 → 模型/网络 |
| 引用编号对不上 | 看 `citation_stats.invalid`，非空说明模型编了编号 |
| Agent 一直转圈 | 看 `steps` 里重复的 (action, input)，无进展检测应该已经熔断 |

## 八、怎么扩展

**换大模型**：改 `configs/config.yaml` 的 `llm.base_url/model`，任何 OpenAI 兼容服务都行。
**换 embedding**：改 `embedding.model_name` + **必须 `--reset` 重建索引**。
**加文档类型**（Word/Excel）：在 `ingest/loader.py` 加分支，返回 `list[PageText]` 即可，下游不用动。
**加 Agent 工具**：在 `agent/tools.py` 的 `build_tools` 里加一个 `Tool`，写好 description 和参数说明。
**加评测维度**：`eval/evaluator.py` 里加指标函数，`EvalRow` 加字段。
**接前端**：任何能发 HTTP 的客户端都行，协议见 `/docs`。

## 九、v1 → v2 演进（面试可讲的"我改了什么"）

| 维度 | v1（legacy/） | v2 | 为什么改 |
|---|---|---|---|
| 结构 | app.py + api.py 两套平行实现 | 分层包 + 单一装配入口 | 逻辑重复、改一处漏一处 |
| 切分 | 按 `\n` 累加 300 字，无重叠 | 章节结构 + 递归分隔符 + 父子块 | 断句、跨章、无上下文 |
| 向量 | Chroma 默认英文模型 | bge-small-zh + 指令前缀 | 中文召回质量 |
| 检索 | 纯向量 top-3 | 混合召回 + RRF + 精排 | 专有名词/编号召回差 |
| 引用 | 返回整段文本 | chunk_id + 页码 + 章节 + 分数 | 无法核对 |
| 评估 | 无 | 45 条评测集 + 5 指标 + 消融 | "感觉还行"不可交付 |
| 工程 | 密钥硬编码、无测试、无日志 | .env + 45 测试 + trace 日志 + Docker | 不可维护 |
| 能力 | 只有问答 | + 流式 + Agent + 限流 + 监控 | 产品化 |

> 面试话术：不要说"我重写了一遍"，要说"我发现了 v1 的 5 个具体问题，
> 每个问题对应一个改动，改动有评测数据支撑"。
