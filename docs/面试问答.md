## A. 项目整体

### A1. 用一句话介绍这个项目

**结论**：一个可评测、可观测的中文文档问答系统，核心是把 RAG 的"召回质量"做成可量化的工程闭环。

**展开**：用户上传 PDF → 解析清洗 → 结构化切分（父子块）→ bge 向量化入库；
提问时向量 + BM25 双路召回 → RRF 融合 → Cross-Encoder 精排 → 父块回溯 → 带引用生成。
自建 45 条评测集（40 可回答 + 5 无答案），用 recall@4/10/20、MRR、引用准确率驱动每一步优化；
实测精排把 recall@4 从 0.62 提到 0.80。另有 ReAct Agent 做多步任务。

**不要说**："做了一个 RAG Demo，调了 DeepSeek 的 API。" —— 这两句话会被立刻归类为"教程级项目"。

### A2. 为什么做 RAG，而不是微调？

**结论**：这个场景的瓶颈是"知识不在模型里"，不是"模型不会说这个领域的话"，所以该外挂知识而不是改参数。

**展开**：
1. 文档 272 页、15.9 万字，还在更新 → 微调要反复重训，RAG 换文档只要重新入库；
2. 需要**引用溯源**，微调给不出"这句话来自第 3 页"；
3. 微调解决的是"风格/格式/领域表达"，RAG 解决的是"事实"。两者是互补，不是替代。

**追问**："什么情况下你会选微调？" → 答：需要固定的输出格式、领域黑话密集（通用模型听不懂）、
或者要压低延迟/成本（小模型 + LoRA 替代大模型）。我这个项目里，把"结构化输出"交给 schema 校验，
把"领域词"交给 BM25，就没必要微调了。

### A3. 讲一下整体架构

**结论**：九层，一条主线：`ingest → embedding → store → retrieval → llm → rag → agent → api → web`。

**展开**（白板画这个）：

```text
   ┌─────────── 离线 ───────────┐        ┌──────────── 在线 ────────────┐
   PDF/TXT ─ loader ─ cleaner ─ splitter ─ embedder ─┬─ chunks.jsonl（事实源）
                                                     ├─ chroma（向量索引）
                                                     └─ bm25（内存索引）
                                                              │
   用户 ─ Streamlit ─ FastAPI ─ QueryRewrite ─ 双路召回 ─ RRF ─ 精排 ─ 父块回溯
                                                              │
                                            Prompt 组装 ─ LLM ─ 引用校验 ─ SSE 回流
   └────────────────────────────── eval 评测贯穿 ──────────────────────────┘
```

**关键设计**：离线部分产出"可重建的索引"，在线部分只读索引；`services.py` 是唯一装配入口，
所有依赖在那里一次性建好，API/脚本/测试复用同一套装配逻辑。

### A4. 你觉得最难/最有价值的三个点是什么？

**结论**：切分策略、检索融合、评测闭环。

1. **切分**：一开始用定长切，召回全是半句话；改成章节结构 + 父子块之后，
   父块从 280 字涨到 1309 字（每父块 7.4 个子块），"小块检索大块生成"才真正成立。
2. **融合**：纯向量对"第三十二条""学籍异动"这类字面信息很弱，加 BM25 后这类 query 才稳。
3. **评测**：没有评测时所有优化都是"感觉变好了"；有了 40 条集子之后，
   每个改动都能说"recall@4 从多少到多少，代价是延迟多了多少毫秒"。

> 这个回答的结构是"问题 → 动作 → 数字 → 代价"，面试官最爱这种。

### A5. 这个项目上线了吗？QPS 多少？

**结论**：没有生产流量，是单机部署 + 本地压测；我能说清它的容量边界在哪。

**展开**：单进程 FastAPI + 本地 Chroma，CPU 推理。检索链路 30-80ms，
瓶颈在 LLM 生成（网络往返 + 首 token）不在本地。按当前设计，
单机瓶颈会先出现在**精排**（cross-encoder 20 条 × 单条约 30-60ms）和**Chroma 单机**上；
再往上就要把精排换成 batch + GPU、向量库换 Milvus、生成走多副本。

**追问**："怎么做压测？" → locust/k6 打 `/api/v1/search`（不花 token）先测检索容量，
再打 `/ask` 测端到端；看 P95 而不是均值。

### A6. 为什么用 Chroma，不用 Milvus / pgvector？

**结论**：数据量 874 个 chunk，Chroma 够用且零运维；选型要跟数据量匹配，不是越重越好。

**展开**：
- Chroma：嵌入式，`PersistentClient(path=...)` 一个目录就是全部，适合单机、十万级以下；
- Milvus：分布式、要独立部署一套集群，百万级以上才划算；
- pgvector：已经有 Postgres 且想"一个库搞定"时最省事，但混合检索/多路召回要自己写 SQL。

**追问**："要扩到 100 万 chunk 怎么办？" → 向量库换 Milvus/Qdrant，BM25 换 Elasticsearch，
embedding 上 GPU 批量化，检索加缓存（语义缓存 + 前缀缓存）。

### A7. 为什么手写 ReAct，不用 LangChain / LangGraph？

**结论**：这个循环 100 行能写完，框架带来的是抽象成本和版本风险，不是能力。

**展开**：
1. 调试：出问题能直接断点在 while 里，看每一轮的 messages；
2. 面试：终止条件、失败重试、无进展检测这些必须讲到代码级，框架里是黑盒；
3. 依赖：LangChain 每个大版本都改 API，学生项目经不起反复迁移。
**但**：如果要上多 Agent 编排、复杂状态机、human-in-the-loop，LangGraph 的收益就明显了，
那时该用就用——**不是排斥框架，是知道什么时候不需要**。

### A8. 如果数据量涨 10 倍，哪里会先崩？

**结论**：先崩的是 ingest 的耗时和精排延迟，然后是 Chroma 的单机内存。

**展开**（要有层次）：
1. ingest：874 块 31 秒，8740 块约 5 分钟 → 要改成异步任务队列 + 断点续跑；
2. 精排：20 条固定，不随数据量涨 → 这块其实不崩；
3. 检索：Chroma HNSW 单机内存吃紧 → 换 Milvus，加量化（PQ/SQ）；
4. 评测：40 条集子不够，要分层抽样 + LLM Judge 扩量。

## B. 分块与索引

### B1. 你的切分方案是什么？

**结论**：三层——按标题切章节 → 章节内递归切 400 字子块 → 跨章节聚 1200 字父块。

**展开**（打开 `ingest/splitter.py` 讲）：
1. **章节识别**：正则匹配 `第X章/第X节/一、/（一）/1.1`，维护层级栈，得到
   `第二章 学籍管理 > 第二节 学籍异动` 这样的 section 路径；
2. **章节内切分**：分隔符优先级 `\n\n → \n → 。→ ！→ ？→ ；→ ，→ 硬切`，
   递归切到 ≤400 字，再贪心装箱，窗口间回退 80 字做重叠；
3. **父块**：把连续子块累加到 ≥1200 字为一组，子块记 `parent_id`。

**实测**：272 页 → 851 个章节块 → 874 子块（均 178 字）→ 118 父块（均 1309 字）。

### B2. 块切太大、切太小分别会怎样？

**结论**：太大 → 语义被稀释、召回不准且贵；太小 → 语义不完整、答不全。

**展开**：
- 太大：一个 chunk 混进多个主题，向量变成"语义平均值"，和任何 query 都有点像；
  同时进上下文的 token 变多，成本涨、长上下文中间的信息还容易被忽略（lost in the middle）。
- 太小：指代丢失（"该条""上述情形"没有指代对象），检索命中了也答不全，模型只能硬凑 → 幻觉。
- 折中：**小块检索、大块生成**。我的子块 400 字负责被检索，父块 1300 字负责被生成。

**追问**："400 是怎么定的？" → 不是拍脑袋：中文 400 字约 300-400 token，
能容纳 2-3 个完整条款；我试过 200/400/600 三档跑评测（`configs/config.yaml` 一行就能改）。

### B3. 为什么要父子块？父块怎么回溯？

**结论**：检索要精度（小块），生成要上下文（大块），父子块把这两个矛盾解耦。

**展开**：子块带 `parent_id`；检索命中子块后，用 `parent_id` 去 `parents.jsonl` 取父块正文，
并且**同一父块只保留分数最高的一条**——否则同一段 1200 字被喂两遍，浪费 token 还分散注意力。

**坑**：我第一版的父块是按章节聚合的，结果父块平均只有 280 字，和子块差不多大，
small-to-big 完全失效。改成跨章节聚合后才到 1309 字。**这个 bug 是看统计数据发现的，不是看代码。**

### B4. overlap 有什么用？设多少？

**结论**：防止答案正好被切在边界上，代价是索引变大、有重复内容。

**展开**：80 字 ≈ 一句话。设置时 `overlap ≤ chunk_size / 2`（我在 `splitter._pack` 里做了钳制），
否则窗口永远在重叠、切不动。副作用：相邻 chunk 内容重复，所以父块回溯时必须去重。

### B5. 文档里有表格怎么办？

**结论**：做成开关，默认关；这是显式的取舍，不是没做。

**展开**：`ingest.extract_tables=true` 时用 pdfplumber 抽表格，转成 Markdown 表格追加到该页文本。
为什么默认关：pdfplumber 按坐标布局解析，一页 1-2 秒，272 页从 4 秒涨到几分钟，
收益只在"文档真有很多表格"时才明显。更好的做法是表格单独建索引 + 表格感知的检索。

**追问**："扫描件呢？" → 当前只做检测告警（平均每页 < 30 字 → warning），不做 OCR；
要做就上 PaddleOCR 或直接多模态模型（Qwen-VL），把图片页转成描述再入库。

### B6. 为什么选 bge-small-zh 而不是 bge-m3 / OpenAI embedding？

**结论**：95MB / 512 维 / CPU 上 874 块 30 秒，是"效果够用 + 能在学生机上跑"的平衡点。

**展开**：
- bge-m3：效果更好、支持多语言和长文本，但 2.2GB，CPU 上入库慢一个数量级；
- OpenAI embedding：效果稳，但要钱、要网络、数据出境；
- 我的配置留了 `embedding.model_name`，换模型只要改一行 + `--reset` 重建索引。

**追问**："怎么验证换模型值不值？" → 跑 `scripts/eval.py --presets hybrid`，对比 recall@4/10/20 和 P95 延迟。

### B7. 为什么 query 要加指令前缀，passage 不加？

**结论**：bge 是**非对称检索**训练出来的，训练时 query 侧带指令、passage 侧不带，推理必须一致。

**展开**：指令是"为这个句子生成表示以用于检索相关文章："。不加的话，
短 query 和长 passage 的向量会偏到不同区域，余弦相似度的分布对不上，召回明显变差。
这是 bge 官方用法，也是很多"我用了 bge 但效果不好"的真实原因。

### B8. 换 embedding 模型要注意什么？

**结论**：必须重建索引，否则向量空间不一致，检索"看起来正常但明显变差"。

**展开**：我在 `manifest.json` 里记了 `embedding_model / embedding_dim / chunk_size`，
启动时 `repo.check_compatibility()` 比对，不一致直接 warning。这是 RAG 里最难查的一类 bug——
不报错，只是效果悄悄下降。

### B9. 为什么 chunk 要带 metadata？带了哪些？

**结论**：没有 metadata 就没有引用、没有过滤、没有版本管理。

**展开**：每个 chunk 存 `doc_id / doc_name / section / page / order / parent_id / char_start / char_end`。
- `section + page` → 引用能显示"第 3 章 · 第 12 页"；
- `doc_id` → 支持按文档过滤、删除、重新入库（Chroma `where={"doc_id": ...}`）；
- `char_start/end` → 能回到原文定位，也方便调试切分。

## C. 检索

### C1. 为什么做混合检索？只用向量不行吗？

**结论**：向量擅长语义、BM25 擅长字面，两者互补；中文制度文档里"条款号 + 专有名词"特别多。

**展开**：比如"第三十二条""学籍异动""国家助学贷款"，向量模型容易召回"意思差不多"的段落，
但对编号和术语的精确匹配很弱；BM25 正好相反。我的实现是两路各取 20 条 → RRF 融合。

**追问**："怎么证明混合比单路好？" → `scripts/eval.py --presets vector_only,hybrid`，
同一份评测集、同一套索引，只翻开关，出对比表。

### C2. BM25 的原理？

**结论**：TF-IDF 的改良版，用饱和函数抑制"词频线性增长"，用文档长度归一化抑制"长文档占优"。

**展开**：`score = Σ IDF(qi) · (tf · (k1+1)) / (tf + k1 · (1 - b + b · |d|/avgdl))`，
我用的 `k1=1.5, b=0.75`。IDF 衡量词的稀有度，tf 是词频，|d|/avgdl 是长度归一。
中文要先分词（jieba），并且要有停用词表——但**不能把"学籍"这类领域词当停用词**。

**追问**："BM25 的缺点？" → 不懂同义词和语义泛化（"休学"和"暂停学业"匹配不上），
所以它必须和向量配合，单用会漏。

### C3. RRF 是什么？公式？为什么不用分数加权？

**结论**：`score(d) = Σ weight_i / (k + rank_i(d))`，k 一般 60；只看名次，不看分数。

**展开**：余弦相似度是 0-1 有界值，BM25 是无界实数（可能为负），量纲对不齐。
加权融合要先归一化再调权重，换模型/换语料就要重调；RRF 只用名次，跨模型迁移更稳。
代价：丢掉了"有多相似"的信息，两路都排 1 和一路排 1 一路排 100 的差异被压缩。

**追问**："k=60 的作用？" → 平滑。k 小 → 头部名次权重极大（更"赢家通吃"）；
k 大 → 各名次差异变小（更平缓）。60 是原论文的经验值。

### C4. 为什么要 rerank？两阶段检索的意义？

**结论**：bi-encoder 快但粗，cross-encoder 准但慢，所以"粗排要召回率、精排要准确率"。

**展开**：
- 向量检索是 bi-encoder：query 和 doc 各自编码成向量再算余弦，**两者没见过彼此**；
- cross-encoder 把 `(query, doc)` 拼起来送进模型做逐词交互，相关性判断明显更准，
  但只能实时算，不能预先建索引。
所以只对召回的前 20 条做，取 top-4。这是工业界标准做法。

**追问**："rerank 的延迟？" → CPU 上 20 条约 0.6-1.2 秒（batch=8），是本地链路里最慢的一环。
优化：减候选数、换更小的 reranker、GPU 批量化、或者只对 top-10 重排。

### C5. Top-K 召回有噪声怎么办？

**结论**：五层递进的手段，我用了前三层。

**展开**：
1. **精排**（cross-encoder）→ 最有效，直接重排；
2. **分数阈值**截断明显不相关的（我的实现留了接口，默认不设，因为阈值要按语料调）；
3. **去冗余**（MMR，词面 Jaccard 近似）→ 我的 `mmr_lambda=1.0` 默认关，因为制度文档重复度低；
4. **改 query**：改写、拆解、HyDE（生成假设答案再检索）；
5. **metadata 过滤**：按文档/章节缩小范围。

### C6. 你的召回率怎么评估？评测集怎么建的？

**结论**：45 条人工题（40 可回答 + 5 无答案），gold chunk 用"高区分度关键词"自动对齐，跑 recall@4/10/20 + MRR。

**展开**：人工写"问题 + 标准答案 + 3 个关键词"（如"累计不得超过两年"），
`scripts/build_eval_set.py` 在 874 个 chunk 里按关键词定位，回填 `gold_chunk_ids`。
关键词命中超过 5 个 chunk 会告警"区分度不足"，避免 gold 标注含糊。
好处：可追溯、可复查、改文档后能自动重新对齐。

**追问**："为什么不用 LLM 自动生成评测集？" → 可以，但 LLM 生成的问题偏"维基式"，
和真实用户问法差距大；我的做法是人工写问题（真实问法）+ 脚本对齐 gold（省人力），各取所长。

### C7. recall@k 和 MRR 的区别？

**结论**：recall 只看"有没有捞到"，MRR 还看"排得靠不靠前"。

**展开**：
- `recall@4`：gold chunk 是否出现在前 4 条，是 0/1；
- `MRR`：第一个正确结果的排名倒数（排第 1 得 1.0，排第 3 得 0.33），最后取平均。

为什么两个都要：召回有了但排在第 20 位，等于没用（被 top-4 截掉了），MRR 能暴露这个问题。

### C8. 查询改写怎么做？多轮怎么处理指代？

**结论**：只在"有指代或问题很短"时触发 LLM 改写，失败退回原问题。

**展开**：`QueryRewriter.needs_rewrite()` 判断：历史非空 +（长度 ≤12 或含"它/这个/上述/该"）。
改写 prompt 要求"补全指代、不增加新信息、只输出问题本身"。
两道闸：改写失败/超时 → 用原问题；结果缓存（同问题同历史只改一次）。

**追问**："改写会不会引入错误？" → 会。所以它是"优化项"不是"必需项"，
失败必须优雅退回；并且改写结果会写进 debug，方便排查是"改写错了"还是"召回错了"。

### C9. 检索延迟怎么拆？怎么优化？

**结论**：先拆再优化，我的 `timings_ms` 记录了 rewrite / vector / bm25 / fuse / rerank / context 六段。

**展开**（实测数量级）：embed 10-20ms、向量 5-15ms、BM25 5-10ms、融合 <1ms、
**精排 600-1200ms**（CPU）、上下文组装 <5ms。所以优化优先级：精排 > embedding > 向量库。

优化手段：并行召回（向量和 BM25 可以并发）、缓存 embedding 和语义结果、
精排减候选数或上 GPU、流式先把首 token 吐出去。

### C10. MMR 是什么？为什么默认关了？

**结论**：最大边际相关，在"相关性"和"多样性"之间做权衡，用来去掉高度重复的结果。

**展开**：`score = λ·relevance - (1-λ)·max_sim(已选)`。我的相似度用词面 Jaccard 近似
（再算一遍向量太贵）。默认 `λ=1.0` 即关闭，因为制度文档切块重复度低，
开了反而可能把"同一章的另一条款"这种有用信息挤掉。

### C11. 为什么 BM25 索引放内存、每次启动重建？

**结论**：874 个 chunk 分词只要 0.5 秒，重建成本远低于维护持久化索引的复杂度。

**展开**：`bm25_index.py` 启动时从 `chunks.jsonl` 重建，jieba 有缓存（0.56s）。
如果 chunk 上万，就要持久化 token 化结果（pickle/parquet）或者上 ES。

### C12. 如果用户问的问题文档里根本没有，会发生什么？

**结论**：检索仍会返回 top-k（相似度低），所以靠 Prompt 约束 + 评测里的"拒答率"兜。

**展开**：Prompt 明确"资料不足就说文档中未提及"；评测集里放了 5 条无答案题，
专门算 `refusal_accuracy`。更强的做法是加"相关性阈值"或让模型先判断"资料是否足够"。

## D. 生成与引用

### D1. 你的 Prompt 怎么写的？

**结论**：角色 + 三条硬规则 + 编号化上下文 + 输出格式要求。

**展开**（`rag/prompts.py`）：
```text
你是 DocQA，一个严格基于给定文档回答问题的助手。
规则：1) 只能用【参考资料】里的信息；2) 每个结论后标 [n]，编号必须来自资料；
     3) 资料不足直接说"文档中未提及"；4) 不编造数字/日期/条款号。
【参考资料】[1] 《手册》第X章 · 第N页 \n 正文...
【问题】...
```
**为什么这么写**：规则要可执行、可检查。"不要编造"是软约束，
"编号必须来自资料"是硬约束——后者能用代码校验。

### D2. 怎么防幻觉？

**结论**：四道闸，从检索到生成到后处理。

**展开**：
1. 检索层：召回不到就不生成（`if not contexts: return "未提及"`），直接掐断编造的机会；
2. Prompt 层：只允许用资料、要求标引用、无答案就明说；
3. 后处理层：**引用校验**——解析回答里的 `[n]`，检查是否越界，越界就是幻觉信号；
4. 评测层：无答案题算拒答率，regression 时能发现"改完 prompt 开始瞎编了"。

**追问**："引用校验能发现所有幻觉吗？" → 不能。编号合法但内容断章取义的情况它抓不到，
那需要 NLI 式的"答案是否被原文蕴含"校验，成本高，我留作后续。

### D3. 引用是怎么做出来的？前端怎么用？

**结论**：chunk 带页码/章节 → 生成时编号 → 返回 `citations[]` → 前端可点开看原文片段。

**展开**：`build_citations()` 把每个 ContextItem 转成 `{index, chunk_id, doc_name, section, page,
snippet, score}`。前端 Streamlit 用 expander 展示，用户能看到"第 12 页 · 第二章 · 相关度 0.83"。
`citation_stats.coverage`（带引用的句子占比）会显示在回答下方。

### D4. 检索内容和模型自身知识冲突怎么办？

**结论**：以资料为准，并且要求模型显式指出冲突，而不是悄悄选一个。

**展开**：Prompt 里"只能使用参考资料"，所以默认以资料为准。更好的做法是加一条规则：
"如果资料与你的常识冲突，先按资料回答，并注明'资料如此记载'"。
这在学校制度、企业内部文档场景很重要——**资料的时效性优先于模型训练数据**。

### D5. 上下文超长怎么办？

**结论**：三层控制——chunk 大小、top_k、总字符预算。

**展开**：`max_context_chars=4000` 是硬预算，超了从低分开始截；
父块本身限制在 1200 字；`final_top_k=4` 控制条数。
再往上就要做上下文压缩（抽取式摘要）或分层摘要（先摘要每个父块再拼）。

### D6. 流式怎么实现的？

**结论**：生成器 + SSE，四类事件：`retrieval / delta / done / error`。

**展开**：`answerer.stream()` 先 yield 一个 `retrieval` 事件（把引用先推给前端，用户马上能看到来源），
然后逐 token yield `delta`，最后 `done` 带引用统计和延迟。
API 层 `StreamingResponse(media_type="text/event-stream")`，每个事件 `data: {...}\n\n`，
末尾 `data: [DONE]`。**关键细节**：加 `X-Accel-Buffering: no`，否则 nginx 会缓冲，流式变一次性返回。

### D7. token 成本怎么控制？

**结论**：能省的三处都省了。

**展开**：
1. 检索为空不调模型（省一次完整调用）；
2. 查询改写只在需要时触发（不是每轮都改）；
3. `final_top_k=4` + 4000 字预算，不让上下文无限膨胀；
4. 响应里带 `usage`（prompt/completion tokens），`/metrics` 能看累计。

### D8. 多轮对话怎么处理？历史怎么放？

**结论**：历史只放最近 4 轮进 prompt，检索用的是改写后的独立问题。

**展开**：`_build_messages` 里 `history[-rewrite_history_turns:]`。
为什么不放全部：token 线性增长、早期历史会干扰当前问题。
为什么检索要用改写后的问题：否则"那第二学期呢"这种 query 检索不到任何东西。

## E. Agent

### E1. 你的 Agent 是什么范式？

**结论**：ReAct（Reasoning + Acting），思考一步、行动一步、看结果再思考。

**展开**：每轮模型输出 `{thought, action, action_input}`，我解析后执行工具，
把观察结果作为下一轮输入。终止条件是 `final_answer` 或触发熔断。

**对比**：Plan-and-Execute 是先出完整计划再执行，适合步骤可预判的任务；
ReAct 更适合"每一步依赖上一步真实返回"的探索型任务，比如"先查有哪些文档，再决定查哪份"。

### E2. 怎么防死循环？

**结论**：四道闸，不只靠最大步数。

**展开**：
1. `max_steps=5`（兜底）；
2. **无进展检测**：`(action, action_input)` 签名相同超过 2 次 → 熔断并提示"换思路"；
3. `max_tool_calls=8`（防止一步里疯狂调工具）；
4. 模型主动 `final_answer`。

**追问**："步数用完还没结论怎么办？" → `_fallback_answer()`：把已有观察拼起来让模型收尾，
返回"部分结果 + 说明缺什么"，比直接抛"超出最大步数"体验好得多。

### E3. 工具调用失败怎么处理？

**结论**：分类处理，把错误当观察回灌给模型，让它自纠。

**展开**：
- 参数不匹配（`TypeError`）→ "参数不正确，请检查参数名和类型"；
- 工具内部异常 → "工具执行失败（原因），请换个方式"；
- 工具不存在 → 列出可用工具名；
- 重复调用 → 提示"你已经这样调过了"。

**为什么不直接抛异常**：模型有能力根据错误信息换参数重试，前提是你把错误告诉它。
这是"可恢复错误"和"不可恢复错误"的区别。

### E4. 工具的描述（description）怎么写才准？

**结论**：写"什么时候用它"，不是"它是什么"。

**展开**：我的 `search_docs` 描述是"在知识库中检索与问题相关的文档片段。
**回答任何关于文档内容的问题前，都应该先调用它**"——后半句是行为约束，
直接影响模型会不会偷懒不检索。参数要少、有默认值、有取值范围（`top_k: 1-8，默认 4`）。

### E5. MCP 和 Function Calling 的区别？

**结论**：Function Calling 是模型侧的"结构化调用意图"，MCP 是工程侧的"工具接入协议"。

**展开**：
- Function Calling：模型按 schema 输出"我要调 X，参数是 Y"，本质还是把工具定义塞进 prompt；
- MCP：把工具/资源/提示模板抽成标准化协议，客户端和服务端解耦，换模型、换工具不用改胶水代码。
代价是多一层进程/传输开销、调试链路变长。

**追问**："你项目里用 MCP 了吗？" → 没有。我的工具是进程内 Python 函数，
4 个工具、单机场景，上 MCP 是过度设计。**但我知道什么规模该上**：工具跨团队复用、
需要权限隔离、要接第三方 SaaS 的时候。

### E6. Agent 的记忆怎么做？

**结论**：我这个项目只做了"单次任务的观察累积"，没有做长期记忆——这是明确的取舍。

**展开**：ReAct 循环里的 messages 就是工作记忆（本轮的工具返回）。
真正的记忆要分三层：working（当前轮中间状态）、short-term（会话历史 + 滚动摘要）、
long-term（跨会话的用户偏好/事实，落库检索）。
**每层都要回答"什么时候写、什么时候召回、冲突谁覆盖、怎么过期"**——只答"存了什么"会显得没设计过。

### E7. 什么时候需要多 Agent？为什么不是单 Agent？

**结论**：当子任务需要不同工具集/不同 prompt/不同权限，且可以并行或独立评估时才拆。

**展开**：拆的代价是通信成本、幻觉放大（A 的错误被 B 当事实）、状态同步复杂。
我的场景（查文档 + 算数）用单 Agent 4 个工具就够了；
如果是"调研 + 写代码 + 测试"这种，才值得拆成 researcher / coder / reviewer。

### E8. Agent 的效果怎么评估？

**结论**：能力评测（能不能做完）+ 过程评测（走了多少弯路）+ 成本（步数/token）。

**展开**：
- 成功率：任务完成率（人工判定或规则校验）；
- 效率：平均步数、工具调用次数、延迟；
- 质量：答案正确性（关键词/人工）、引用准确率；
- 失败模式分布：是"检索不到"、"工具用错"还是"不会收尾"——这决定你下一步改什么。

### E9. 你的 Agent 有什么已知问题？

**结论**：在没有强模型时容易"过度检索"，以及缺少 human-in-the-loop。

**展开**：Mock 模式下 Agent 直接给 final_answer；真实模型下偶尔会连续调用 `search_docs` 换措辞，
无进展检测能拦住但答案质量会打折。改进方向：给工具加"已查过"的状态提示、
让模型先输出计划再执行、加人工确认节点（危险操作前）。

## F. 工程化

### F1. 为什么拆成 FastAPI + Streamlit，不做成单文件？

**结论**：单文件 Demo 的所有逻辑都长在 UI 里，换个前端就重写；分离后接口是契约。

**展开**：Streamlit 只做 `requests` 调用，后端可以独立部署、独立压测、被任何客户端复用（小程序/飞书机器人）。
v1 就是"两套平行实现"（app.py 自己调 OpenAI，api.py 另写一份），
改一处漏一处，README 还写着"前后端分离"——这是最容易被面试官抓的矛盾点，v2 彻底改掉了。

### F2. 密钥怎么管理？

**结论**：`.env` + `.gitignore` + 环境变量覆盖，代码里零硬编码。

**展开**：`.env.example` 只放占位符，`.env` 被 gitignore；
配置走 pydantic-settings，`DOCQA_LLM__API_KEY` 注入；
`/api/v1/config` 接口明确不返回密钥（有测试断言 `api_key not in body`）。

**加分故事**：v1 的 Key 硬编码在 `app.py` 里，还进了 git 历史。我发现后做了三件事：
吊销旧 Key、用 `git filter-repo` 清历史、改成环境变量。**这段可以主动讲**——
说明你知道"密钥泄露"的完整处置流程，而不只是"不要硬编码"。

### F3. Docker 怎么部署？

**结论**：`python:3.12-slim` + 非 root 用户 + CPU 版 torch + 健康检查，compose 起 api 和 web。

**展开**：镜像里 `pip install --extra-index-url https://download.pytorch.org/whl/cpu .`，
不指定的话会拉 2GB+ 的 CUDA 轮子；`data/` 挂卷（索引、模型缓存不進镜像）；
`HEALTHCHECK` 打 `/api/v1/health`；`compose` 里 web 通过服务名 `http://api:8000` 访问后端。

### F4. 并发和限流怎么做的？

**结论**：FastAPI 异步 + 线程池跑 CPU 任务 + 进程内令牌桶。

**展开**：`run_in_threadpool` 把同步的检索/生成丢到线程池，避免阻塞事件循环；
中间件里做 60 秒滑动窗口限流（默认 120 次/分钟），超了返回 429。
单机限流只是"防误刷"，真正的限流要在网关层（Nginx/Kong）做。

### F5. 日志和可观测性怎么做的？

**结论**：trace_id + 结构化日志 + 阶段计时 + 指标接口。

**展开**：每个请求分配 `trace_id`（响应头 `X-Trace-Id` 回写），日志里带上，
一次请求的"改写后 query、各阶段命中数、耗时"都能按 id 串起来；
`/api/v1/metrics` 返回请求数、错误数、平均延迟、索引统计；
`RetrievalDebug.timings_ms` 是每次请求的六段耗时——**这是定位性能问题的第一现场**。

### F6. 测试怎么做的？覆盖了什么？

**结论**：45 个测试，纯离线（哈希 embedding + Mock LLM），10 秒跑完。

**展开**：切分器（标题识别、块大小、父子包含、页码映射、ID 唯一）、
检索（RRF 顺序、权重、MMR、引用校验）、存储（入库幂等、删除、manifest 兼容性）、
API（健康、上传、问答、流式 SSE、422/404、metrics）、Agent（JSON 容错、安全计算器、终止条件）。

**关键设计**：测试**不下载模型、不联网**——这靠 `Embedder` 接口 + 哈希实现做到。
没有这个抽象，测试要等 95MB 下载，没人会跑。

### F7. 索引更新/文档多版本怎么处理？

**结论**：doc_id 用内容哈希，重新入库先删旧向量；多版本靠 metadata 过滤。

**展开**：同一文件改名重传 → 哈希相同 → 覆盖而不是新增（有测试）；
删除文档 → 按 `where={"doc_id": ...}` 删向量 + 从 jsonl 里移除。
多版本共存的完整做法：chunk 打 `doc_id + version + status`，检索时按 metadata 过滤生效版本，
"先写新版本再切指针"保证可回滚。我做了 doc_id 级别的替换，版本级是下一步。

### F8. 如果让你优化首 token 时间？

**结论**：先拆解（检索 vs 生成），再分别下手。

**展开**：本地检索 30-80ms 不是瓶颈；瓶颈是 LLM 首 token（网络 + 模型排队）。
手段：流式（已做，用户 1 秒内看到字）、减少 prompt 长度（top_k=4 + 4000 字预算）、
缓存（相同问题语义缓存）、换更快的模型/就近地域、把精排挪到异步（先返回粗排结果再更新）。

### F9. 你这个项目的代码质量怎么保证？

**结论**：分层 + 类型注解 + Pydantic 校验 + ruff + 测试 + 文档。

**展开**：跨层数据全用 Pydantic 模型（不是裸 dict），接口自动生成 OpenAPI；
`ruff` 做 lint（line-length 100）；关键路径有测试；`docs/` 写了学习手册和面试问答——
**"能讲清楚"本身也是工程质量的一部分**。

## G. 评测

### G1. 你怎么证明这个 RAG 有效？

**结论**：40 条人工评测集 + 四个指标 + 消融对比表。

**展开**：`recall@4` 证明检索能捞到、`MRR` 证明排得靠前、
`keyword_hit` 证明答案对、`citation_precision` 证明引用是真依据。
消融：`vector_only → hybrid → hybrid+rerank`，每一档的提升都能报数字。

### G2. 为什么不全用 LLM 打分（LLM-as-Judge）？

**结论**：LLM 打分适合开放性答案，但成本高、不稳定、有位置偏见；能用规则算的就别用模型。

**展开**：我的场景答案相对封闭（条款、数字），关键词命中 + 引用校验已经够用，还免费、可复现。
LLM Judge 的正确用法是**初筛**：几百条里挑出可疑的，再人工抽验，而不是直接当最终分。

### G3. 评测集只有 40 条，够吗？

**结论**：不够做统计显著性，够做方向判断。这是学生项目的现实约束，我知道它的边界。

**展开**：40 条能发现"改动带来 10 个百分点级别的变化"，发现不了 2 个点的差异。
要更严谨：分层抽样到 200+ 条（按意图/难度/是否有答案分层）、多次运行取均值、
算置信区间。**主动说出局限，比假装严谨加分。**

### G4. 线上 badcase 怎么回流？

**结论**：现在没有线上流量，但设计了回流路径。

**展开**：`/ask` 返回 `trace_id` + `debug`，前端可以"点踩 + 原因"，
后端按 trace_id 把 query、召回结果、回答存成 badcase；
badcase 归集成新评测集 → 改检索/prompt → 跑回归，防止修好一个坏一个。

### G5. 你怎么做回归测试？

**结论**：`scripts/eval.py` 就是回归工具，每次改完跑一遍对比。

**展开**：报告落到 `data/eval/reports/`（JSON + Markdown 两种），
JSON 用来 diff 指标，Markdown 用来贴周报/简历。

### G6. 如果 recall 很高但答案还是错，问题在哪？

**结论**：在"检索到了但没用上"——排序、上下文组织、或 Prompt。

**展开**：按顺序排查：
1. gold chunk 进了 top-k，但被 `final_top_k` 截掉了 → 调 top_k 或加精排；
2. 进了上下文，但被更长的无关内容挤掉（lost in the middle）→ 调整顺序/压缩；
3. 上下文够了但模型没引用 → Prompt 或模型能力问题。
`debug` 字段能同时看到"召回列表"和"最终上下文"，一眼定位。

## H. 收尾与反问

### H1. 你觉得这个项目最大的短板是什么？

**结论**：没有真实用户和线上流量，所以"效果"是离线评测出来的，不是业务验证的。

**展开**（三个层次，别只说一个）：
1. 数据规模：单文档 874 块，混合检索的收益在更大规模、更多文档类型上还没验证；
2. 评测：40 条，只能看方向，看不了统计显著性；
3. 产品：没有多租户、权限、增量更新、badcase 闭环。
**但**：这些短板我都知道"如果要补，第一步做什么"——这比假装没有短板强。

### H2. 如果重做一遍，你会怎么改？

**结论**：先建评测集，再写检索。

**展开**：这次我是"先写完再补评测"，结果前期很多改动没法验证；
正确顺序是：拿 20 条真实问题 → 建最小评测 → 写 baseline（纯向量）→ 每加一个组件跑一次。
另外会把 ingest 做成异步任务（现在 272 页同步 31 秒，大文档会阻塞请求）。

### H3. 你最近在学什么？

**结论**：往"评测 + 推理优化"两个方向补。

**展开**：评测——RAGAS 那套自动评测怎么和人工标注对齐；
推理——vLLM / KV cache / 首 token 延迟优化，因为这决定 RAG 能不能做到"像搜索一样快"。

### H4. 你还有什么想问我的？

**准备三个**（按团队类型选）：
1. 团队现在的 RAG 系统，最大的瓶颈是在检索还是在生成？
2. 你们怎么评估线上效果？有没有 badcase 回流机制？
3. 这个岗位前三个月，最希望我先把哪块补齐？

> 反问的作用不是"显得礼貌"，是让对方觉得"这人已经在用工程师的方式思考了"。

### H5. 一句话总结你从这个项目学到什么？

**结论**：RAG 的瓶颈几乎从来不是"模型不够强"，而是"检索没给对材料"。

**展开**：我最初以为接上大模型就完事了，结果 80% 的时间花在解析、清洗、切分、
召回融合上；每提升一次召回质量，回答质量就肉眼可见地变好。
这也改变了我看 AI 应用的方式——**应用层的护城河在数据和工程，不在调参。**
